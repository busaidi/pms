# تعليمات نشر PMS لكودكس

هذا الدليل لتحديث البرودكشن الموجود، وليس إنشاء بيانات بديلة. اقرأه قبل تنفيذ أي نشر.

## قواعد إلزامية

- لا تستعد `pms-data.zip` أو قاعدة اللوكال فوق البرودكشن. لا تستخدم `flush` أو `seed_demo` أو `loaddata` لنسخة البيانات المحلية.
- لا تحذف قاعدة أو عقارًا أو مستأجرًا أو عقدًا أو فاتورة. لا تعدّل أرقامها أو روابطها لتسهيل الاستيراد.
- لا تنقل `.env` أو `.local-postgres` من اللوكال. استخدم إعدادات وأسرار السيرفر الحالية. لا تطبع كلمات المرور أو محتويات حزمة التوقيع.
- لا تستخدم `git clean -fdx` أو تحذف ملفات المستخدم. لا تستبدل إعداد خدمة مخصصًا بقالب الريبو بلا مقارنة.
- لا تغيّر الشروط أو بيانات المؤجر أو التوقيع الموجودة عند حدوث تعارض. الاستيراد يتوقف عمدًا؛ اعرض التعارض واطلب قرارًا محددًا.
- لا تعتبر نجاح الاختبارات المحلية إثباتًا لنجاح النشر. تحقق من الخدمة وملف PDF الناتج تحت مستخدم الخدمة.
- إذا لم يكن اتصال السيرفر أو النشر مأذونًا في جلسة التنفيذ، جهّز المعاينة فقط قبل طلب الإذن. هذا الدليل ليس إذنًا دائمًا بالاتصال بأي سيرفر.

## ما يصل عبر Git وما يصل منفصلًا

Git: الكود، migrations، قوالب HTML، Tajawal، Quill، سكربت PDF، ملفات النشر.
خارج Git: حزمة `*.contract-bundle.json` تحتوي قوالب الشروط وإعدادات المؤجر وصورة توقيعه فقط. تعامل معها كملف خاص، وليست ملفًا عامًا أو مشفرًا.
لا تحتوي الحزمة مستأجرين أو عقودًا أو فواتير أو مرفقات هويات أو كلمات مرور أو PDF تاريخية.

الحزمة المحلية المحضرة: `artifacts/deployment/production.contract-bundle.json`.
البصمة في الملف المجاور `production.sha256.txt`. كلاهما خارج Git؛ الكلون وحده لا يجلبهما.
إذا كانت الحزمة غير موجودة في بيئة كودكس على السيرفر، اطلب نقلها عبر اتصال خاص مع البصمة، ولا تحاول إعادة إنشائها من بيانات السيرفر.
إذا عدّل المستخدم القوالب بعد تجهيزها، صدّر حزمة جديدة باسم جديد باستخدام:

```powershell
.venv\Scripts\python.exe manage.py export_contract_config artifacts/deployment/updated.contract-bundle.json
```

يفترض المصدر PostgreSQL المحلي المستعاد من البرودكشن. اربط العقار باستخدام تطابق `slug` و`name`، وليس رقمه فقط. أداة الاستيراد لا تنشئ عقارات ولا تسمح بتجاوز اختلاف الهوية.

## 1. اكتشاف السيرفر والنسخ الاحتياطي

تحقق من اتصال موثوق، مسار المشروع، مستخدم الخدمة، ملف systemd الفعلي، إعداد Nginx، ومصدر بيئة قاعدة البيانات. الافتراضات في الريبو هي `/home/hamed/pms` ومستخدم `pms` وقاعدة `pms`؛ تحقق منها ولا تعتمدها عميانيًا.
سجّل commit الحالي ونسخة الخدمة، وخذ نسخة جديدة من قاعدة البرودكشن و`media/` و`private-contracts/` إن وجد. خزّنها خارج الريبو بصلاحيات مقيدة، وتحقق من إمكانية قراءة فهرس dump. لا تستخدم ملف الباك أب المحلي القديم كنسخة تراجع.
خطط لنافذة صيانة توقف الكتابة عند أخذ النسخة وتطبيق التحديث. احتفظ بالأسرار الحالية خارج Git.

## 2. تجهيز الاعتماديات والتخزين

داخل نسخة الكود الجديدة وببيئة Python الخاصة بالسيرفر:

```bash
pip install -r requirements.txt
npm ci
```

ثبّت متطلبات Chromium للنظام بصلاحيات المسؤول ثم Chromium بحساب `pms`:

```bash
sudo npx playwright install-deps chromium
sudo -u pms -H npx playwright install chromium
```

نفذ الأوامر من جذر المشروع. تحقق من أن حساب الخدمة يملك HOME صالحًا وقابلًا للكتابة أثناء التثبيت. إذا استُخدم `PLAYWRIGHT_BROWSERS_PATH` فاجعله نفسه في التثبيت وبيئة systemd وفي الفحوصات. لا تفترض أن تثبيت المتصفح بحساب root يجعله متاحًا لحساب الخدمة.

أنشئ `private-contracts/` قبل إعادة تشغيل الخدمة (المسار التالي مشروط بتأكيد مسار المشروع):

```bash
sudo install -d -o pms -g www-data -m 0750 /home/hamed/pms/private-contracts
```

راجع فرق `deployment/pms.service` و`deployment/pms-celery.service`: كلاهما يحتاج `ReadWritePaths` لمجلد العقود بالإضافة إلى media بسبب `ProtectSystem=strict` و`ProtectHome=read-only`.
ادمج التعديل في الخدمة الفعلية أو drop-in ثم `systemctl daemon-reload`. إذا تغيّر `LEASE_CONTRACT_ROOT`، حدّث صلاحيات ومسار systemd وفقه أيضًا. لا تعرض private-contracts من Nginx.
المتغيران `LEASE_CONTRACT_ROOT` و`CONTRACT_NODE_EXECUTABLE` مقروءان من البيئة. تأكد من وجود Node على PATH الخاص بالخدمة.

## 3. تهيئة Django والاستيراد

شغّل أوامر Django بحساب الخدمة وبنفس إعداداته وأسراره. أوامر shell لا ترث بيئة systemd تلقائيًا. استخدم `DJANGO_ENV=production` وتحقق من مضيف واسم قاعدة البيانات قبل أي كتابة. لا تضع كلمات المرور في سطر الأوامر.

```bash
python manage.py check --deploy
python manage.py migrate --plan
python manage.py migrate --noinput
python manage.py collectstatic --noinput
```

راجع خطة migrations؛ هذا الإصدار يتضمن 0009–0014 في properties. لا تستخدم `--fake`. لا تفتح شاشة القوالب أو تولّد عقدًا قبل الاستيراد، لأن ذلك قد ينشئ قالبًا افتراضيًا ويؤدي لتعارض محافظ.
انقل الحزمة إلى مجلد خاص مقروء لحساب الخدمة، مثل `/var/lib/pms-transfer/production.contract-bundle.json`، بصلاحيات ملف 0600 ومجلد 0700 ومالك pms. تحقق من SHA256 مقابل البصمة القادمة من اللوكال عبر قناة موثوقة.

معاينة فقط (بلا كتابة):

```bash
python manage.py import_contract_config /var/lib/pms-transfer/production.contract-bundle.json
```

راجع العقارات وعدد القوالب الجديدة والإعدادات التي ستُضاف. الأمر يرفض التعارض على كامل الحزمة قبل التنفيذ، ويتخطى السجلات المطابقة. لا توجد خاصية overwrite.
بعد اعتماد الهدف والمعاينة، نفّذ باستبدال القيم بين الأقواس:

```bash
python manage.py import_contract_config /var/lib/pms-transfer/production.contract-bundle.json --apply --sha256 <VERIFIED_SHA256> --database-name <VERIFIED_DB_NAME> --actor <EXISTING_ACTIVE_SUPERUSER_USERNAME>
```

التطبيق يعيد التحقق داخل transaction، ويسجل التغييرات باسم المستخدم المحدد في سجل التدقيق. لا يعدّل ربط العقود القديمة بالقوالب ولا نسخ PDF القديمة. عند فشل العملية تُلغى تغييرات القاعدة وتُزال ملفات التوقيع الجديدة الخاصة بالمحاولة. لا ينشئ المستخدم الإداري؛ يجب أن يكون موجودًا مسبقًا.
أعد المعاينة بعد التطبيق: يجب ألا تقترح إضافات أخرى. لا تحذف الحزمة حتى يكتمل التحقق؛ بعدها احفظها ضمن النسخ الخاصة أو احذف النسخة المؤقتة حسب سياسة الموقع.

## 4. التحقق قبل إعادة فتح النظام

- أعد تشغيل الخدمات المتأثرة وتأكد من active وعدم ظهور أخطاء في journal.
- تحقق من تسجيل الدخول والصلاحيات، تحميل المحرر والخطوط، ظهور القوالب الصحيحة وتوقيع المؤجر في إعدادات العقار.
- استخدم معاينة قالب دون حفظ عقد تجريبي: تحقق من الغلاف والخط والشروط والتوقيع وفراغ توقيع المستأجر. اختبر PDF بحساب الخدمة؛ لا يكفي تشغيله بحساب SSH.
- تأكد أن مجلد العقود قابل للكتابة من داخل قيود الخدمة، وأن روابط الملفات الخاصة لا تعمل بلا صلاحية.
- قارن أعداد العقارات والمستأجرين والعقود والفواتير والأرصدة بما قبل نافذة الصيانة؛ استيراد الإعدادات لا يغيّرها. الزيادات المتوقعة فقط هي القوالب وملفات تعريف المؤجر وسجلات التدقيق.
- تحقق من تنبيهات انتهاء العقود وعدم تحرير الوحدة قبل التسليم.
- لا تنشئ عقدًا أو فاتورة اختبار في قاعدة الإنتاج لمجرد التحقق؛ اختبارات الكتابة تعمل على قاعدة اختبار منفصلة.

## التراجع والتقرير

عند فشل الاعتماديات أو PDF أوقف فتح الخدمة للمستخدمين، وشخّص السبب. لا تستعد قاعدة قديمة تلقائيًا ولا تعكس migrations حذفًا للجداول الجديدة. الرجوع للكود السابق يجب أن يراعي توافقه مع الـ schema، ويترك الجداول الإضافية وبياناتها محفوظة. استعادة قاعدة البيانات قرار مستقل إذا ثبتت الحاجة، وبعد تأكيد عدم فقد معاملات لاحقة.
في تقريرك اذكر commit المنشور، نسخة الباك أب، اسم القاعدة التي تحققت منها دون أسرار، نتيجة migrations والاستيراد، وفحص PDF والخدمات. فرّق بين نجاح clone/pull وبين نجاح النشر الفعلي. إذا توقفت عند تعارض، اذكره ولا تقل إن النشر اكتمل.
